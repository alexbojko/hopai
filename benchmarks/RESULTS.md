## 05 — Findings

**Where the library layer costs most.** `Q12` (AND(OR(...), {...})) ran 5.2x the raw statement (62.1 ms vs 12.0 ms) over 5,431 nodes. The gap is result mapping and property hydration, and it is roughly fixed per call -- so it dominates a small answer and shrinks against a large one. Read it next to the row count, never alone.

**What aggregating instead of traversing saves.** `Q27` runs `Q14`'s chain and returns a number instead of a subgraph: 2,235.2 ms against 4,351.8 ms, **1.9x**. Same walk, same match set -- the difference is the edge-reconstruction CTEs and the property hydration that a count does not need. Pairs measured: `Q19`/`Q3` 1.1x, `Q25`/`Q5` 1.1x, `Q26`/`Q7` 1.0x, `Q27`/`Q14` 1.9x.

**Answers that disagree.** `Q6` hopai 6 vs Neo4j 5; `Q6` hopai 6 vs AGE 5; `Q7` hopai 226 vs AGE 225. A speed comparison between systems returning different results is not a comparison -- these are flagged rather than smoothed over, and are worth resolving before quoting the timings beside them.

**Where the alternatives fall over.** `Q4` (Backward bounded <=3 hops) took 62,878 ms on AGE against 14.3 ms here -- 4,397x. Traversal is where the gap opens; plain property filters are competitive on every system.

**Queries that measured nothing.** `Q1`, `Q18`, `Q20`, `Q23`, `Q24` returned zero rows. Finding nothing is always fast, so these timings describe the dataset, not the engine.

**Noisy measurements.** `Q11`, `Q18`, `Q23` varied by more than 50% between warm runs. Their medians are not comparable across commits; re-run on a quiet machine before drawing a conclusion from them.
