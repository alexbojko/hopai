## 05 — Findings

**Where the library layer costs most.** `Q11` (BETWEEN range comparison) ran 7.2x the raw statement (92.4 ms vs 12.8 ms) over 2,970 nodes. The gap is result mapping and property hydration, and it is roughly fixed per call -- so it dominates a small answer and shrinks against a large one. Read it next to the row count, never alone.

**What aggregating instead of traversing saves.** `Q27` runs `Q14`'s chain and returns a number instead of a subgraph: 92.5 ms against 411.7 ms, **4.5x**. Same walk, same match set -- the difference is the edge-reconstruction CTEs and the property hydration that a count does not need. Pairs measured: `Q19`/`Q3` 1.2x, `Q25`/`Q5` 1.1x, `Q26`/`Q7` 1.0x, `Q27`/`Q14` 4.5x.

**Queries that measured nothing.** `Q1`, `Q18`, `Q20`, `Q23`, `Q24` returned zero rows. Finding nothing is always fast, so these timings describe the dataset, not the engine.

**Noisy measurements.** `Q8`, `Q11`, `Q25`, `Q26` varied by more than 50% between warm runs. Their medians are not comparable across commits; re-run on a quiet machine before drawing a conclusion from them.

Synthetic data: a sparse random background DAG plus a deliberately structured hub subgraph with real fan-in across several depth levels — the shape that stresses a traversal engine, which a purely random graph does not.
